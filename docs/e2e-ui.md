# UI E2E: реальный браузер против стейджинга

`npm run test:e2e` — весь UI-цикл в headless chromium без участия человека.
Тесты живут в `e2e/` этого репозитория: они версионируются вместе с UI,
который проверяют, и любое изменение разметки чинится в том же PR, который
его внёс. Отдельный репозиторий не даёт здесь ничего, кроме рассинхрона.

## Как обойдён passkey

Никакой специальной сборки нет — тестируется боевой код. Playwright
подключает к странице CDP Virtual Authenticator (`e2e/fixtures.ts`):
платформенный аутентификатор с user verification и автоподтверждением
presence. Все вызовы `navigator.credentials` — создание паскея, разблокировка
vault — резолвятся молча, а `isUserVerifyingPlatformAuthenticatorAvailable()`
честно отвечает true. Продакшен-путь WebAuthn выполняется целиком.

## Правила, выведенные из реальных падений

- **Навигация только внутренняя** (клики по меню). `page.goto()` — полная
  перезагрузка SPA: vault блокируется, приложение уходит на логин-экран.
  Перезагрузка и повторный вход — отдельный сценарий, а не побочный эффект.
- **Пара аккаунтов — worker-scoped и создаётся конкурентно** (~80 с на аккаунт
  об стейджинг). Одна пара обслуживает все тесты воркера; тесты получают
  диалог с настоящей историей.
- **Один воркер.** Стейджинг общий, диалоги статeful; параллелизм — позже.
- Имена аккаунтов уникальны на прогон (`e2e-<роль>-<runId>`) и служат ключом
  поиска: ручное добавление собеседника = поиск по имени в списке, без QR.
- Ожидания кросс-аккаунтной синхронизации — до 90 с: карточка и сообщение
  едут через шейпы стейджинга.

## Ограничения

- Каждый прогон оставляет на стейджинге свежие user_cards/сообщения — как и
  протокольный `e2e.staging.test.ts`; приемлемо, пока стейджинг тестовый.
- Бинарные браузеры приходят из образа контейнера (`/ms-playwright`);
  `PLAYWRIGHT_BROWSERS_PATH` прошит в npm-скрипте.
- В CI набор не включён: прогон стоит минуты и зависит от живого стейджинга.
  Запуск — руками или по расписанию; включение в CI обсудим, когда набор
  стабилизируется.
