# Reviews: что уже есть на бэкенде

Контекст для работы над фичей отзывов. Источник — репозиторий `Buckitup-chat/chat`,
коммит `867607a`; спека целиком: `docs/pq/proposal/reviews.md` (919 строк).

## Главное

**Серверная часть реализована и закрыта тестами.** В реестре шейпов
(`lib/chat/data/shapes.ex`) зарегистрировано 9 review/origin-шейпов, миграции
применены, конвейер модерации работает во всех трёх режимах, 241 тест зелёный.
Отдельных HTTP-маршрутов у фичи нет: всё идёт через те же `/ingest`,
`/ingest_each` и `/electric/v1/shapes`, что и остальные таблицы.

**Не сделано — клиент.** В `chat-frontend` ноль упоминаний origins и reviews.
Спека помечает это как `UI ✗` в обеих фазах.

То есть если задача звучит как «сделать бэкенд для отзывов» — стоит сперва
свериться: возможно, речь про недостающие куски (см. «Чего на бэкенде нет»),
про отдельный сервис, или про клиент. Ниже — то, на что можно опираться.

## Модель

Отзыв — про **origin** (заведение, площадка). Origin это не комната, а
**субаккаунт**: у него собственная строка в `user_cards` со своей парой
ML-DSA-87 + ML-KEM-1024, и владелец-пользователь, связанный через `owner_cert`.
Из этого следует важное: приватный отзыв «в личку заведению» (`to_origin`)
**не требует ничего нового** — это обычное сообщение диалога на `user_hash`
origin'а, вся машинерия `pq_dialogs` работает как есть. Отдельные таблицы
существуют только ради публичных отзывов (`to_public`).

Видимость публичного отзыва контролирует **сервер**, а не автор. Содержимое
отзыва зашифровано `review_password`; отзыв становится читаемым публично
только когда пароль появляется в `review_public_passwords`. Автор не может
писать в эту таблицу — он подаёт «кандидата», а сервер промотирует.

## Таблицы и шейпы

| Таблица (`?table=`) | Назначение | Синкается |
|---|---|---|
| `origins` | метаданные заведения, `moderation_mode`, `owner_cert` | да |
| `review` | сам отзыв, `content_b64` зашифрован `review_password` | да, по `origin_hash` |
| `review_public_passwords` | пароли публичных отзывов; append-only, LWW по `owner_timestamp`, `password_b64 = null` = отозван | да |
| `review_list` | список `(review_hash, review_password)` автора для контактов | да, по `user_hash` или `origin_hash` |
| `review_post_right` | KEM-конверт: право опубликовать | да |
| `review_revoke_right` | KEM-конверт: право отозвать | да |
| `review_password_candidate` | заявка автора до решения модерации | **нет** (server-internal) |
| `review_post_right_candidate` | стейджинг: конверт до подписи автора | да (автору) |
| `review_revoke_right_candidate` | то же для отзыва права | да (автору) |

Префиксы хешей (`lib/chat/data/types/consts.ex`): `ors_` (origin sign),
`rv_` (review id), `rvs_` (review sign), `rvps_` (password sign),
`rvprs_` / `rvrrs_` (post/revoke right sign), `rvls_` (review_list sign).
Все — `prefix + hex(SHA3-512)`, как у диалоговых.

## Эндпоинты

Никаких review-специфичных маршрутов нет:

- **чтение** — `GET /electric/v1/shapes?table=<таблица>&where=…`; таблицы из
  списка выше проходят `ElectricTableGuard` (он собирает вайтлист из реестра
  шейпов на этапе компиляции);
- **запись** — `POST /electric/v1/ingest_each` с обычной мутацией; таблицу
  задаёт `syncMetadata.relation`, значения совпадают с именами шейпов:
  `"review"`, `"review_list"`, `"review_public_passwords"`, `"origin"` и т. д.;
- **аутентификация** — тот же challenge/PoP, что и везде.

Пример мутации из теста бэкенда
(`test/chat_web/controllers/electric_controller_review_test.exs:296`):

```json
{
  "type": "insert",
  "modified": {
    "review_hash": "rv_…", "origin_hash": "u_…", "author_hash": "u_…",
    "content_b64": "…", "deleted_flag": false,
    "owner_timestamp": 1234567890, "sign_b64": "…", "sign_hash": "rvs_…"
  },
  "syncMetadata": { "relation": "review" }
}
```

## Три режима модерации

Режим выбирает владелец origin'а (`origins.moderation_mode`).

- **`none`** — сервер промотирует пароль сразу, отзыв публичен немедленно.
- **`post`** — автор сначала выдаёт право отзыва (revoke), сервер публикует,
  origin может скрыть позже.
- **`pre`** — автор выдаёт оба права, сервер держит пароль у себя, публикация
  происходит действием origin'а.

Промоушен — **двухфазное рукопожатие через обычный ingest**, без отдельных
маршрутов. Фаза 1 (`promote_candidate`) срабатывает на приход кандидатов и
заворачивает пароль в KEM-конверт на `crypt_pkey` origin'а. Фаза 2
(`complete_promotion`) срабатывает, когда автор дочитал конверт из шейпа,
проверил обёртку и прислал подпись; сервер переносит подписанные кандидаты в
боевые таблицы.

Жёсткий инвариант, который придётся соблюдать клиенту: в режимах `post` и `pre`
`owner_timestamp` null-версии (revoke) должен быть **строго больше**, чем у
версии с паролем, иначе отзыв не перекроет публикацию по LWW. Сервер это
проверяет и отклоняет промоушен.

## Контакты видят отзыв в обход модерации

У автора есть `review_list` — по строке на отзыв, где `review_password`
зашифрован единым на автора `review_list_password`. Сам `review_list_password`
раздаётся контактам через диалог и лежит в User Storage для мультидевайса.
**Сущности контактов в данных нет** — список контактов целиком клиентский,
сервер видит только строки `review_list`.

Чтобы контакты не стали лазейкой мимо модерации, `review_list` требует
доказательств прохождения конвейера; сервер проверяет их и на insert, и на
update:

| Режим | `review_password_sign_hash` | `post_right_sign_hash` | `revoke_right_sign_hash` |
|---|---|---|---|
| `none` | обязателен | null | null |
| `post` | обязателен | null | обязателен |
| `pre` | null до одобрения, затем заполняется | обязателен | обязателен |

## Готовые референсы — песочницы

Самое ценное для клиентской работы: на бэкенде живут работающие LiveView-реализации
всех ролей. Это не макеты, они ходят в тот же API и проверены на живом сервере
во всех трёх режимах.

| URL | Роль |
|---|---|
| `/electric/origin_sandbox` | создание origin'а, экспорт/импорт ключей |
| `/electric/review_sandbox` | автор: написать отзыв, подать кандидатов, подписать права, собрать `review_list` |
| `/electric/moderation_sandbox` | origin: импорт identity, очередь, approve / reject / revoke |
| `/electric/contacts_reader` | читатель: собрать ключи из диалогов, прочитать отзывы контактов |
| `/electric/origin_reviews` | публичный просмотр расшифрованных отзывов |
| `/electric/origins`, `/electric/reviews`, `/electric/review_lists`, `/electric/review_public_passwords`, `/electric/review_post_rights`, `/electric/review_revoke_rights` | справочники строк |

## Чего на бэкенде нет

Из спеки, раздел «Known gaps» и Phase 3/5:

- **Разделение владелец / origin не enforced.** Смена `moderation_mode` и
  soft-delete origin'а авторизуются подписью **origin identity**, то есть
  делегированный модератор может это сделать. Требование «опасные операции
  подписывает владелец» отложено.
- **Устаревший update по HTTP отдаёт 500 вместо 4xx** — changeset помечается
  `:ignore`, а `Ecto.Multi.update` его не принимает. Затрагивает все
  ingest-таблицы, не только review.
- **Равные `owner_timestamp` расходятся между узлом и пирами** — локально
  проходит, у пиров отвергается. `owner_timestamp` в секундах, так что два
  клика в одну секунду попадают в это. Ровно та же проблема, что мы решали
  через `nextOwnerTimestamp`.
- **Кандидаты паролей не проверяются по подписи на ingest** — плохо подписанный
  кандидат сохраняется и возвращает `{:ok, :pending}`; до боевой таблицы он не
  доходит, но и не удаляется никогда.
- **Нет сборки мусора** ни для `review_password_candidate`, ни для неподписанных
  right-кандидатов. Функция `delete_stale_candidates/1` существует, но её никто
  не вызывает.
- **Комментарии не спроектированы** — отложены намеренно.
- **Метаданные origin'а** — в таблице только `name`; ни адреса, ни категории,
  ни геопоиска. Открытый вопрос спеки.
- **Discovery origin'ов** — только «показать все».
- **Цепочка версий отзыва** — `parent_sign_hash` хранится и update работает, но
  корректность цепочки никто не валидирует и ни один клиент правок не пишет.

## Что уточнить перед стартом

1. Что именно понимается под «новый бэкенд»: недостающие куски из списка выше,
   отдельный сервис, или всё-таки клиентская часть?
2. Метаданные origin'а и discovery — это первое, что упрётся в продуктовое
   решение, и это чистая доработка бэкенда.
3. Комментарии — если они в объёме, их проектирование ещё не начато.
