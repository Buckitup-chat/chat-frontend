# План: персистентность локального состояния и outbox

**Дата:** 2026-08-11
**Ветка:** `docs/tanstack-migration` (вершина стека PR #21–#25)
**Статус:** план на согласование, код не написан

---

## 1. Задача

Сейчас клиентское состояние живёт **в оперативной памяти**: коллекции TanStack
DB наполняются из Electric-шейпов при каждом старте, исходящие мутации
существуют только как промисы в памяти. Единственное, что персистится, —
`user_storage` через простой IndexedDB KV (`src/lib/data/localStore.ts`).

Из этого следуют две разные проблемы, которые важно не путать:

| | Что теряется | Симптом |
|---|---|---|
| **A. Чтение** | История диалогов, карточки пользователей | Без связи с узлом ничего не видно; при каждом старте всё качается заново |
| **B. Запись (outbox)** | Неотправленные исходящие мутации | Закрыл вкладку / пропала связь → сообщение исчезло молча |

Оба ревью отмечали именно **B** как главный пробел offline-first. **A** — это
скорее скорость старта и работа в дороге.

Важно: речь про разрыв **браузер ↔ локальный узел (Raspberry Pi)**. Отсутствие
интернета при живом узле у нас и так работает — это архитектура продукта.

---

## 2. Ключевое ограничение: подпись привязана к состоянию сервера

Это то, что делает наш outbox **не** типовым.

Мутации подписываются ML-DSA против **известной базы на сервере**:
`parent_sign_hash` — это `sign_hash` текущей ревизии, `owner_timestamp` должен
строго возрастать. Мы сознательно решили (находка 1 второго ревью) **не
подписывать от неизвестной базы** — иначе гарантированный 422 при
восстановлении связи.

Отсюда следует, что операции делятся на два класса:

**Класс 1 — самодостаточные (можно подписать сразу и хранить подписанными):**
- новое сообщение (`dialog_messages` insert): `message_id` генерирует клиент,
  `parent_sign_hash = null`. От состояния сервера не зависит.
- Оговорка: `refs_map` считается от загруженных сообщений, то есть «что я видел
  на момент отправки» — это как раз корректная семантика и в офлайне.

**Класс 2 — зависимые от базы (хранить можно только намерение, подписывать при
отправке):**
- редактирование сообщения (`update` с `parent_sign_hash` = текущий tip);
- реакции (insert или update — зависит от наличия строки, включая тумбстоун);
- `user_storage` (профиль, контакты, аватар);
- `user_card` (переименование).

**Практический вывод:** outbox должен уметь оба режима. Для класса 2 хранится
неподписанное намерение, которое материализуется в подписанную мутацию в
момент доставки, когда база известна.

**Второе следствие:** подпись требует приватного ключа из vault, а он
заблокирован до аутентификации (WebAuthn). Значит **флаш очереди происходит не
при загрузке страницы, а после логина**. Для класса 1 теоретически можно было
бы доставить и без ключа (подпись уже есть), но проще и честнее — единый
момент флаша.

## 3. Развилка по инструментам

### Вариант 1 — свой outbox на существующем IndexedDB KV

Расширить `localStore.ts` (уже работает, проверен, используется для
`user_storage`) отдельным object store для очереди.

- **Плюсы:** ноль новых зависимостей; полный контроль над семантикой
  «намерение vs подписанная мутация», которая у нас нетиповая; ~200–300 строк;
  тестируется юнитами без браузера.
- **Минусы:** пишем сами; не решает задачу **A** (персистентность чтения).

### Вариант 2 — официальная персистентность TanStack DB

Доступно на сегодня:
- `@tanstack/db-sqlite-persistence-core` 0.2.9
- `@tanstack/browser-db-sqlite-persistence` 0.2.9 — **требует peer
  `@journeyapps/wa-sqlite`, то есть WASM SQLite**
- `@tanstack/offline-transactions` 1.0.42 — зависит от `@tanstack/db` 0.6.17
  (ровно наша версия), но в peerDeps указаны `react-native` и
  `@react-native-community/netinfo` — пригодность для браузера требует
  проверки.

Официально персистентность работает и для синхронизируемых (Electric)
коллекций, и есть виртуальное поле `$synced` для отслеживания
локальных/оптимистичных строк.

- **Плюсы:** решает **A** и **B** разом; поддерживается апстримом; `$synced`
  бесплатно даёт индикацию доставки.
- **Минусы, которые нельзя игнорировать:**
  1. **Это альфа** (прямая формулировка в блоге TanStack про 0.6).
  2. **Возвращает WASM-базу в браузер.** Мы только что удалили PGlite именно
     из-за WASM+IndexedDB на горячем пути. Роль другая (SQLite здесь — write-
     behind кэш, а запросы остаются в памяти), и wa-sqlite кратно легче
     PGlite — но утверждать это без замера нельзя. У нас есть готовая
     методика замера с прошлого раза.
  3. Не снимает ограничение из раздела 2: подписи всё равно наши, и «хранить
     подписанное намерение класса 2» апстрим за нас не решит.

### Рекомендация

**Идти вариантом 1 для outbox, вариант 2 оценить отдельно и позже для
персистентности чтения.**

Обоснование: outbox — это то, где теряются пользовательские данные, и его
семантика у нас специфична из-за подписей; тащить ради него альфа-зависимость
с WASM-базой несоразмерно. Персистентность чтения (A) — отдельная задача с
понятной пользой (быстрый старт, чтение в дороге), и вот там официальный
адаптер уместен — но только после замера, что мы не воспроизводим проблему
PGlite.

## 4. Этапы

### Этап 1 — Хранилище очереди (фундамент)
`src/lib/data/outbox.ts` + расширение `localStore.ts` вторым object store.

Запись очереди:
```ts
type OutboxEntry = {
  id: string;                    // uuid
  userHash: string;              // очередь приватна для аккаунта
  kind: 'signed' | 'intent';     // класс 1 / класс 2 из раздела 2
  relation: string;              // dialog_messages, ...
  payload: unknown;              // подписанная мутация ИЛИ описание намерения
  createdAt: number;
  attempts: number;
  lastError?: string;
  status: 'pending' | 'sending' | 'failed_permanent';
};
```
Операции: `enqueue`, `listPending(userHash)`, `markSending`, `remove`,
`markPermanentFailure`. Строго FIFO по `createdAt` внутри одного `relation`,
чтобы не нарушить порядок ревизий.

**Тесты:** сохранение/чтение переживает пересоздание соединения с БД;
изоляция по `userHash`; порядок FIFO.

### Этап 2 — Материализация намерений
Функция, превращающая `intent` в подписанную мутацию в момент доставки:
читает актуальную базу (`getServerState` / коллекция), выбирает
insert-vs-update, ставит `nextOwnerTimestamp`, подписывает.

Здесь же — политика конфликтов: если базы нет (узел недоступен) — оставить в
очереди; если сервер отверг permanently — `failed_permanent` + видимый статус.

**Тесты:** намерение «поставить реакцию» превращается в insert, если строки
нет, и в update, если есть тумбстоун; при недоступном узле остаётся в очереди
и ничего не подписывает.

### Этап 3 — Флаш и интеграция с путём отправки
- Единая точка: попытка отправки → при недоступности узла кладём в outbox
  вместо тихой потери.
- Флаш запускается: после логина, при восстановлении связи (сигнал от
  `attach.ts`), и по таймеру с backoff.
- Уважать существующий барьер `sendMutationsAndAwaitShape` — очередь
  доставляет строго последовательно, чтобы `parent_sign_hash` следующей
  ревизии считался от уже видимого в шейпе состояния.

**Тесты:** сообщение, отправленное при недоступном узле, попадает в очередь;
после «восстановления» доставляется; повторный флаш не создаёт дубль.

### Этап 4 — Отражение в UI
- Сообщение из очереди показывается с честным статусом (не «отправлено»).
- Индикатор «N не отправлено» + причина для `failed_permanent`.
- Переиспользовать существующий паттерн статусов реакций
  (`reaction-error` из фиксов второго ревью).

### Этап 5 (отдельное решение) — Персистентность чтения
Прототип на `@tanstack/browser-db-sqlite-persistence` для одной коллекции,
**с замером по методике прошлого раза** (холодный старт, время до первого
рендера, размер бандла). Решение принимать по цифрам: если WASM-персистентность
возвращает нас к секундам старта — отказаться и рассмотреть простой IndexedDB
снапшот последних N сообщений на диалог.

## 5. Открытые вопросы (нужно решение до этапа 3–4)

1. **Срок жизни очереди.** Сколько держать неотправленное сообщение —
   сутки, неделю, бессрочно? Влияет на GC и на честность UI.
2. **Порядок vs блокировка.** Если первое сообщение в очереди не проходит
   permanently, остальные — пропускать или блокировать очередь? Для чата
   логичнее пропускать (сообщения независимы), но для правок одного
   сообщения порядок критичен.
3. **Мультивкладочность.** Две вкладки одного аккаунта разделяют IndexedDB.
   Нужен ли лидер-лок на флаш, чтобы не дублировать отправку? (Сейчас
   приложение и так предупреждает «open in another tab» — возможно, вопрос
   снимается.)
4. **Шифрование очереди.** В outbox лежит уже зашифрованный контент
   (`content_b64`), но для класса 2 намерение может содержать открытый текст
   до шифрования. Хранить намерения зашифрованными или считать IndexedDB
   достаточно защищённым? Для privacy-продукта требует явного ответа.

---

## 6. Оценка и порядок

Этапы 1–3 — ядро, дают то, ради чего всё затевалось (не терять записи).
Этап 4 — обязателен, иначе очередь невидима пользователю.
Этап 5 — отдельная задача, можно не делать сейчас.

Предлагаю начать с этапа 1 и остановиться на ответах к вопросам 1–2 раздела 5,
поскольку они меняют логику этапа 3.
