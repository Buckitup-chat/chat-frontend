# Задержка доставки сообщений: замер и разбор

**Дата замера:** 2026-08-14
**Сборка:** ветка `docs/tanstack-migration`, коммит `2ffd2c1`, dev-сервер Vite
**Бэкенд:** `https://buckitup.xyz`, Electric поверх Postgres (перезапущен
незадолго до замера)
**Клиент:** TanStack DB + `@tanstack/electric-db-collection`, шейпы через
`/electric/v1/shapes`

---

## 1. Коротко

Сообщения между двумя участниками диалога доставляются **пачками**, а не по
мере отправки. Три сообщения, отправленные с интервалом 8 секунд, пришли
получателю **в одну и ту же миллисекунду**. Наблюдаемая задержка — от 1 до 17
секунд, и определяется она не нагрузкой, а тем, в какой момент цикла
long-poll попала отправка.

В сетевом слое получателя видно, что два подряд запроса `live=true` провисели
по 20.2 секунды и вернули «изменений нет», хотя часть сообщений к этому
моменту уже была отправлена.

**Важная оговорка, которую нельзя пропускать:** собранных данных
**недостаточно**, чтобы отличить «читатель не увидел вовремя» от «писатель
записал позже, чем кажется». Обе гипотезы описаны в §5, и там же — конкретный
замер, который их разделяет. Прошу не считать это подтверждённым багом
Electric, пока §6 не выполнен.

---

## 2. Как воспроизведено

Два независимых сеанса приложения в одном браузере. Приложение запрещает
вторую вкладку, поэтому сеансы разведены по origin:

| Сеанс | Origin | Аккаунт |
|---|---|---|
| Отправитель | `http://b.localhost:5174` | `ClaudeTest-C` — `u_5cbb0089…d9b06c` |
| Получатель | `http://localhost:5174` | `ClaudeTest-B` — `u_c6098dc8…5607b0` |

Chrome отображает любой `*.localhost` на loopback; это отдельное хранилище и
при этом валидный RP ID для WebAuthn (`127.0.0.1` не подошёл бы — WebAuthn не
принимает IP-адреса). Оба сеанса ходят на один и тот же dev-сервер и один и тот
же бэкенд.

Обе стороны держали диалог **открытым** всё время замера. Это существенно: см.
§7.

Отправка выполнялась программно — установка значения в поле ввода и клик по
кнопке отправки, с фиксацией `Date.now()` непосредственно перед кликом.
Получатель фиксировал появление текста в DOM через `MutationObserver` плюс
опрос каждые 50 мс.

## 4. Сетевой слой получателя

Запросы шейпа `dialog_messages` у получателя, из
`performance.getEntriesByType('resource')`. `start`/`dur` — миллисекунды от
загрузки страницы; `size` — `decodedBodySize`.

```
live  offset            start   dur     size
true  0_inf             51669     464   7232
true  150786056_0       52136   20221     73     ← «изменений нет»
true  150786056_0       72358   20238     73     ← «изменений нет»
true  150786056_0       92597    3535   7461     ← пришли все три
true  150792376_0       96134     483   7461
true  150798696_0       96619     375   7461
```

Всего запросов к шейпам диалога: 9, из них `live=true`: 6.
Паузы между окончанием одного long-poll и началом следующего: **3, 1, 1, 2, 2
мс** — клиент переоткрывает соединение немедленно, простоя на его стороне нет.

### Привязка к общим часам

Точка отсчёта выведена из совпадения момента отрисовки и окончания запроса,
доставившего данные: `1786701885212 − 96132 ≈ 1786701789080`.

| Запрос | Начало (wall) | Конец (wall) | Длит. | Размер | Что вернул |
|---|---|---|---|---|---|
| A | 1786701840749 | 1786701841213 | 464 мс | 7232 | снимок (`offset=0_inf`) |
| B | 1786701841216 | 1786701861437 | 20 221 мс | 73 | нет изменений |
| **C** | 1786701861438 | 1786701881676 | 20 238 мс | 73 | **нет изменений** |
| **D** | 1786701881677 | 1786701885212 | 3 535 мс | 7461 | **все три сообщения** |
| E | 1786701885214 | 1786701885697 | 483 мс | 7461 | — |
| F | 1786701885699 | 1786701886074 | 375 мс | 7461 | — |

Наложение отправок на этот таймлайн:

```
C: [1786701861438 ─────────────────────────────── 1786701881676]  → 73 байта
        ↑ msg1 1786701868207          ↑ msg2 1786701876206
D: [1786701881677 ────────── 1786701885212]                        → 7461 байт
        ↑ msg3 1786701884207
```

- **msg1** отправлено за 13.5 с до конца запроса C — C вернул «нет изменений».
- **msg2** отправлено за 5.5 с до конца запроса C — C вернул «нет изменений».
- **msg3** отправлено во время запроса D — D завершился через **1.0 с** после
  него и принёс сразу все три.

Обратите внимание: `offset` в запросах B, C и D **один и тот же** —
`150786056_0`. То есть с точки зрения сервера позиция в логе шейпа за это время
не сдвинулась.

## 5. Две гипотезы

Наблюдение «D проснулся через 1.0 с после msg3, а C не проснулся вовсе за 13.5
с» допускает два объяснения, и они принципиально разные.

### Гипотеза 1 — читатель: long-poll не будится записью, случившейся во время ожидания

Запрос C провисел полный таймаут (20.2 с) и вернул `up-to-date` без данных,
хотя записи уже были в логе. Механизм пробуждения сработал для D, но не для C.

*Что за неё:* D проснулся раньше своего таймаута — значит пробуждение в
принципе работает, и молчание C выглядит как пропуск уведомления. Одинаковый
offset у B, C и D говорит, что сервер всё это время считал позицию неизменной.

*Что против:* непонятно, почему механизм сработал в одном случае и не сработал
в двух других подряд.

### Гипотеза 2 — писатель: коммиты произошли позже, чем зафиксирована отправка

Замер фиксирует момент **клика**, а не момент коммита в Postgres. Путь записи в
клиенте асинхронный: подпись ML-DSA, HTTP-запрос, затем барьер
`sendMutationsAndAwaitShape`, ожидающий видимости txid. Если сам POST у
отправителя занял секунды (или встал в очередь), то msg1 и msg2 могли попасть в
Postgres лишь около 1786701884–885, то есть **уже во время запроса D**. Тогда
поведение сервера безупречно: C честно не видел данных, потому что их не было,
а D отдал всё, что появилось.

*Что за неё:* объясняет одновременное прибытие без всяких пропусков
уведомлений, и объясняет, почему D сработал «правильно».

*Что против:* нужно, чтобы две записи подряд задержались на 8–16 с, что само по
себе тоже проблема — просто в другом месте.

**Обе гипотезы означают проблему, но чинить их надо в разных местах.**
Гипотеза 1 — сторона Electric. Гипотеза 2 — путь записи (клиент или приём
мутаций на сервере).

## 6. Что нужно измерить, чтобы их разделить

Достаточно одного прогона с добавленной фиксацией на стороне отправителя.

1. **Время коммита у отправителя.** Записать `Date.now()` в трёх точках: перед
   отправкой HTTP-запроса мутации, при получении ответа `200`, и при
   срабатывании барьера видимости txid. Если ответ `200` приходит через
   секунды — гипотеза 2, и дальше копать надо в приём мутаций.
2. **Серверная правда.** Для трёх записей взять из Postgres
   `xact_commit_timestamp` (или `inserted_at`, если такая колонка есть) и
   сравнить с моментами клика. Это снимает вопрос окончательно.
3. **Лог Electric** за интервал `1786701861438–1786701885212`: приходило ли
   уведомление об изменении шейпа `dialog_messages` с фильтром
   `dialog_hash = '<хеш диалога C↔B>'`, и в какой момент.

Если пункт 2 покажет, что коммиты были в момент клика — подтверждается гипотеза
1, и вопрос переходит к Electric. Если коммиты поздние — вопрос к пути записи.

## 7. Побочная находка: диалоги не синхронизируются в фоне

До того как получатель **открыл** диалог, его вкладка не сделала **ни одного**
запроса к шейпам диалога:

```
tables: ["user_cards", "user_storage"]   ← за 48 запросов к /api/shapes
dialogReqs: 0
```

Сообщение, отправленное в этот период, не приходило вовсе — ни через 15 секунд,
ни позже. Оно появилось сразу после открытия диалога, когда клиент завёл
подписку (14 запросов).

Это отдельное от §3 поведение: диалоговые коллекции создаются лениво, по
`dialog_hash` открытого диалога. Для пользователя это выглядит как «сообщения
приходят только когда откроешь чат» — и легко смешивается с задержкой из §3,
хотя причина другая.

Требует продуктового решения: либо фоновая подписка на все диалоги
пользователя, либо отдельный лёгкий канал уведомлений.

## 8. Приложение: вес шейпа `user_cards`

Замерено тогда же, к задержке доставки отношения не имеет, но влияет на
ощущение «медленно» при старте.

```
GET /electric/v1/shapes?table=user_cards&offset=-1
  → 200, 740 080 байт, 30 строк           (~24 КБ на карточку: ML-DSA/ML-KEM ключи и сертификаты)

GET /electric/v1/shapes?table=user_cards&offset=0_0&handle=…&live=true
  → 200, 2 075 992 байта, 112 записей лога
```

В логе 75 различных ключей, одна карточка встречается **27 раз** — каждое
переименование публикует строку целиком. Итого около **2.8 МБ**, чтобы клиент
вышел в `up-to-date`.

Сжатия нет: запрос с `Accept-Encoding: gzip, br` возвращает те же 740 080 байт.
Локально `gzip -9` срезает 25% (740 080 → 551 481 и 2 075 992 → 1 534 602).

Байты кэшируются браузером (`cache-control: public, max-age=604800`), поэтому
при обычной перезагрузке сеть не нагружается — но разбор JSON и раскладка в
коллекцию повторяются на каждом старте.

**Предложение бэкенду:** включить gzip на эндпоинте шейпов. Правка на стороне
сервера, выигрыш получают все клиенты сразу.

## 9. Как воспроизвести

```bash
git checkout docs/tanstack-migration
npm install --legacy-peer-deps
npm run dev
```

Открыть `http://localhost:5174` и `http://b.localhost:5174`, завести в каждом по
аккаунту, добавить один другому в контакты по `user_hash`, открыть диалог с
обеих сторон и отправлять сообщения с интервалом ~8 секунд, засекая время
клика и время появления у получателя.

Смотреть в DevTools → Network фильтр `live=true`: длительность каждого запроса
и размер ответа. Ответ в ~73 байта — это «изменений нет».
